# KITT 离线知识工厂：调查、整理、跨 AI 协作与 GitHub 发布协议 V1.0

> **定稿日期 2026-10-14。** 这是《[KITT 离线知识内容与生产标准 V1.0](KITT_KNOWLEDGE_STANDARD.md)》的**生产操作协议**。前者规定产品身份、知识范围、L0—L6 来源用途、A—D 证据等级、普通游客表达和事实/版权底线；本文规定**谁做、怎样验证、怎样交接、GitHub 放哪里、何时发布**。如有内容理念矛盾，以上述正式内容标准为准。
>
> **任务边界：** 本文是用户确认的后续多模型知识生产与发布规范，**不是立即启动爬虫、创建新仓库、上传成品、修改 KITT 运行时或扩大正在开发的 V0.4.0/#20 的施工授权**。运行时数据的最终适配在 #20 交付后核对；所有未实际运行的工具、CI、仓库和 Releases 均只能标为 **PLANNED**。

## 1. 一句话架构与权责

**不同 AI 负责研究与编辑 → GitHub Issue/分支/PR 是唯一协作交接 → 校验和必要人工审查 → GitHub Releases 发布独立知识包 → 手机预先下载、校验、完全离线读取。**

三类长期数据**分开保存**：

| 层 | 存什么 | 应存何处 | 禁止 |
| --- | --- | --- | --- |
| **事实源与生产历史** | 已核验来源登记、对象、原子事实、证据定位、冲突处理、游客式编辑元数据、Schema、构建脚本、评审状态 | **规划中的 `KITT-PACKS` Git 仓库**；小文件、文本、可比较/可回退 | 不要按日期复制同一事实，不要提交巨型爬虫缓存或一次性 AI 全量聊天 |
| **正式手机成品** | 版本化的 `.kittpack`/SQLite 或压缩数据、manifest、校验摘要、必要的兼容索引 | **同仓库 GitHub Releases**，按 tag 保存可复现发布版本 | 不要把每个二进制编译结果 commit 到 Git 历史；不要用 GitHub Actions 临时 artifact 作为永久归档 |
| **受限资料与施工缓存** | 未授权分发的县志/书籍全文、扫描 PDF、图片、地图原数据、文献批量下载、私有账号或 API 凭据 | 有权限控制的本机/NAS/合法授权存储；公开 Git 只记合法书目与 locator | 不因文献“可读”就公开镜像；不把访问凭据、地理轨迹、账号或系统私钥提交/回传 |

**已确认分包目标**：全国基础包 + 省级通识包 + 市州/城市详细包；**城市包只依赖基础包，不强制用户先下载整个省包**。跨地区共享山河/历史/工程事实归于最合适的上层包或稳定公共对象引用，城市包只保存独特局部事实；引用不可出现缺失必需包的悬空关系。地图与知识包分开，实时信息不进入稳定离线包。

**仓库阶段**：目前 `shimao1115/KITT` 是 Android App 源码与正式规格的存放处，拟新建 `shimao1115/KITT-PACKS` 专门管知识生产；在用户授权实际建仓/发布前，**不得宣称第二仓库已存在**。也不把受限文献上传给没有对应使用授权的外部 AI 服务。

## 2. 生产的最小粒度：以地区认领、以对象/事实交付

- 一个 **地区任务**：一县/一个镇街或一个跨区域主题，包含适用 `area_id`、地区层级、六类候选内容、预期首批范围、来源策略和完成门禁。首个核验场为**新都区**，不能为凑齐数目编造。
- 一个 **可分工子任务**：一个真实对象/主题（人物、桥、河、村、产业、事件等），或若干独立来源的查证，不按“先历史后补其他”组织。
- **一个原子 Claim 只陈述一件可定位、可核验的事实**。事实与其 Source 使用稳定 ID，变更通过修订/撤销/`supersedes` 留痕，不能删除旧证据后宣称从未存在。
- 同名/别名先做对象归一；跨地区共享对象可以一对象多区域关联，禁止复制成多份相互冲突的人物档案。
- 每个地区先保证自然、工程、人文、生活、历史均有**检索机会**，不是每类强制产出数量。资料稀薄则明确标注调查缺口和真实`SILENT`空间，不注水。

## 3. 多 AI 可以互换角色，但交付物必须统一

**允许任意组合 ChatGPT、Codex、Gemini、DeepSeek、Claude 或其他受授权工具；角色是任务，不是品牌。** 模型强弱影响抽样与验证策略，不能因为“模型A很强”绕过证据门槛。

| 阶段 | 主要工作 | 必须交付的可核查产物 | 不能冒充的成功 |
| --- | --- | --- | --- |
| ① **发现 Scout** | 从 L0—L6 寻找对象、书目、可靠真实入口，规划实际检索缺口 | 候选 ID/别名/地区、Source Registry 草案、可打开 URL/书目、检索边界 | “AI 知道”不算找到来源；不存在链接不得生成 |
| ② **抽取 Extractor** | 真正阅读有权访问的文献，拆原子事实、记定位和适用时段 | ``sources.jsonl` / `claims.jsonl` 草稿、`source_id + locator`、原始网页/页码的读取状态 | 不能把未打开网页、搜索摘要、另一模型结论标成 VERIFIED |
| ③ **复核 Verifier** | 独立重看原始证据、检查来源是否真的支持此句、发现转载同源与冲突 | `supports/contradicts`、状态`verified|contested|lead|rejected`、原因、复核者与时间 | **换模型不是换证据**；未读原文不得签已核实 |
| ④ **游客编辑 Editor** | 融合背景、挑选有趣角度、白话解释、关联真实沿途场景 | `traveler_intro`、`why_interesting`、术语白话、追问方向、引用 claim_id | 不能自行添新事实，不能把“属于本区”写成“眼前就是” |
| ⑤ **校验/构建 Builder** | Schema/引用/权利校验、稳定 ID、重复和时效性检查、构建可安装知识包 | 自动校验报告、可复现构建命令和版本、输出文件 SHA256 | QA 脚本 PASS ≠ 事实/真人听感 PASS |
| ⑥ **发布 Publisher** | 检查审核证据、生成 manifest/catalog、正式 tag 与 release、手机消费兼容性 | Release 链接、tag/commit、包摘要、变更单、许可/来源声明 | 只有管理员/获授权发布者可发正式版本；其他 AI 不能自行宣称发布 |

原则：一套小任务上，一个 AI **可以连做发现、抽取和编辑**，不必为每步开启一个新模型。但**复核必须实际重新查证证据**；若材料有争议/高风险，交由独立资料与有能力的复核者确认，必要时人工终审。**人不必逐条人工操纵流程，但对出版质量、争议、版权和样本讲述负责。**

## 4. GitHub 协作契约：Issue 是工单，PR 是事实交接

**最小交接流程：**

1. 在 `KITT-PACKS` 开 **一个地区 Issue**，填：`task_id`、`area_id`、工作范围、六类检索方向、当前来源、可用版权边界、预期对象、`input_commit`、产物、验收门禁。
2. **一个活跃写入者认领一个任务/子目录**（Issue assignee/状态、分支命名）。同一时段其他模型可审查、提出候选/意见，但**不能同时覆盖同一事实文件**。同一地区可以按对象分多工单/分支，最后按稳定 ID 合并。
3. 每位 Agent 从 GitHub 最新 `main` /指定 commit 接班，仅修改**明确认领的区域/对象文件**，完成后通过独立分支提交 **PR**，附脱敏的发现/抽取/复核摘要和未解决问题。**禁止多模型并发直接推 main**，也不要反复复制旧 `sources` 数据。
4. PR 上由另一个模型或人员**基于原始来源检查关键 Claims**；自动 lint 检查结构、引用和一致性。合格后合并，状态由 `WORKING` → `REVIEW` → `ACCEPTED`；不合格返回 `NEEDS_FIX` 或 `BLOCKED`，并附证据；中断可从工单恢复。
5. 一个地区的已合并内容经测试才可形成**Release candidate**。发布权限集中在获授权的人/受控发布动作；合并 PR ≠ 发布到手机客户端。
6. 后续修改同一事实只更新已有对象和Claim（保留修订关系）并创建新 PR，不能沿日期又起第二个相同事实档案。

建议 Issue 状态：`TODO`、`WORKING`、`REVIEW`、`BLOCKED`、`ACCEPTED`、`RELEASED`；仅`ACCEPTED`内容进入候选包。Claim 的 `lead|verified|contested|rejected` 是**独立事实状态**，不要和工单生命周期混淆。

**工单最少必填**：`task_id`、`area_id`、`scope`、`assignee/tool`、`source_leads`、`paths_owned`、`definition_of_done`、`last_verified_commit`、`blockers`。交接说明只写**结论、证据定位、已做/未做、可继续的明确状态**，不归档巨量聊天或私有链式思考，不把模型生成的推理当文献证明。

工具对 GitHub 的实际读写能力不一样：能调用 GitHub connector/MCP 就按权限建 Issue/PR；不能直连时交付符合 Schema 的文件，由有权限的工具提交。**没有连接不能假装已提交或自动运行。**

## 5. 计划中的 `KITT-PACKS` 目录（先小后大）

```text
KITT-PACKS/                         # PLANNED, not yet created
  README.md                        # 唯一入口、内容标准链接、制作/发布状态
  AGENTS.md                        # 面向任何模型的接班与安全契约
  schemas/                         # 机器验证 JSON Schema 与兼容版本
    kpc.schema.json
    manifest.schema.json
  registry/
    areas.jsonl                    # 可合法发布的区域身份/别名/层级索引
    sources.jsonl                  # 各区/各对象复用的来源目录
  regions/
    cn/51/510100/510114/           # 示例：四川/成都/新都（行政代码需经来源及时代核验）
      inventory.json               # 本区查到/缺失的内容方向、所有对象概览
      entities.jsonl               # 人/事/物实体与关系
      claims.jsonl                 # 原子事实、支持证据与审核状态
      editorial.jsonl              # 面向普通游客的背景、趣味角度、追问线索
      review.json                  # QA 和抽样人审记录
  scripts/
    validate.py                    # 生产格式、引用、许可/状态及时间检查
    build_pack.py                  # 可重复的知识包构建
  catalog/
    catalog.json                   # 已发布包索引，只有出版完成才更新
  docs/
    SOURCE_RULES.md                # 授权、证据分级、禁入项；引用 KITT 正式标准
    OPERATIONS.md                  # Issue/PR/Review/Release 操作流程
  .github/
    ISSUE_TEMPLATE/               # 区域研究工单
    pull_request_template.md      # Claim+证据+审校/构建报告
    workflows/                    # 仅自动校验，发布需受控
```

**为什么这么分**：全国区域身份和来源登记不必每市复制一份；市州包按原子事实/对象组织，便于差异审核；受限原始书籍、网页镜像和大二进制数据**完全不在 Git 仓库**。后续规模很大时可把公用索引拆目录或按省分仓，但**首版不要建几十个 repo、数据库服务器和调度平台**。

**示意事实（不是已核验的历史事实或可直接导入的最终手机 Schema）：**

```json
{
  "claim_id": "clm_510114_example_001",
  "entity_id": "ent_example",
  "area_ids": ["510114"],
  "statement": "【示例占位：未核验，不得发布】",
  "source_refs": [
    {"source_id": "src_example", "locator": "章节/页码或网页小节", "relation": "supports"}
  ],
  "status": "lead",
  "stability": "stable",
  "editorial_ids": []
}
```

正式 Schema 冻结时，以上示例须按 V0.4.0 实际运行数据和正式内容规范校正，不能把示例硬塞到 Android 代码里。

## 6. 两道质量门槛 + 一个发布门槛

**事实审稿（100%正式事实至少一个可定位直接支持它的可靠证据）：**
- URL/出版版本/页码或网页小节真实且与 Claim 一一对应；未读来源不得标`verified`。
- A—D 是**论断证据等级**，L0—L6 是**来源用途分类**，绝不能混为一谈；转载同一内容不算两份独立证据。
- 重大争议/不确定信息按`contested`处理，存在合理谨慎表述才可公开；`lead/rejected` 不进正式讲述。
- 地区归属/时代、官方文物/非遗称谓、精确位置、桥隧参数须按相关最直接资料核对。事实缺失就留空，不补造。
- 版权/采集权与**再分发权分离**；公开内容只能包含允许分发的结构化事实/简短独立撰写概括与来源元数据，不镜像文章、PDF、地图/瓦片、音视频或大段译写。

**游客审稿（第一批新都20–50条小样本全量检查，之后才定义抽样）：**
- 不要求学科背景：先讲清“这里是什么/有什么有趣/为什么如此”，遇术语白话解释。
- 多领域主题均有研究机会，不搞历史优先固定比例；与当前位置有关且实际值得听；一段只讲一个主要重点。
- 严格区分“属于本区”与“车窗外能看见”；当前天气/道路/票价等不从静态资料捏造。
- 用户可追问深入；复述与讲更多不重复已经完整播过的事实。
- 一个题材通过`verified`不代表其游客文字通过，必须**两个审稿 Gate 都 PASS**。

**程序发布 Gate：** JSON Schema、ID唯一/别名归一、跨文件引用存在、版本/依赖完整、hash、确定性构建、禁止lead/rejected、许可检查、安全字段扫描、无原始轨迹/密钥、包在断网设备上可读及已有 app 版本兼容。**事实、人类审稿通过才能真正发布**；CI/Python 绿灯不能替代内容判断。

## 7. 从 Git → Release → 手机的发布契约

- 文件名建议：`cn-51-510100-510114_v2026.10.1.kittpack`（只是格式示例；实际`area_id`以合法可核实标识为准）。`.kittpack` 可先是打包容器 `manifest.json + data.jsonl` 或 `manifest.json + data.sqlite`，**内部格式及 Schema 由 #20 真实交付后冻结**，不要为扩展性立即加入 FTS/向量库。
- `manifest.json` 至少包含：`pack_id`、`region_scope`、`content_version`、`schema_version`、`minimum_app_compatibility`、`dependencies`（基础包） 、`created_at`、`sources_summary`、`rights_summary`、`record_counts`、`file_sha256`、`source_commit`；对文件摘要注意 manifest 自身哈希避免循环引用，可用 release/catalog 外层哈希作完整包摘要。
- 发布：固定输入 commit + schema/validator 构建 → 测试/人审 → 创建不可随意改写的**版本 tag** → Release 上传二进制和对应`SHA256SUMS`/版本说明 → 更新仓库`catalog.json`中可供 App 查询的合法 URL、包兼容性及摘要。包不能在发布后**原地覆盖同一版本**，修订发布新版本，旧版本可回滚。
- **下载安全**：手机根据可信目录查版本，先下载到暂存区，检查哈希/大小/Schema/地区与依赖，验收成功后**原子安装**；失败保留原版本，不要求立刻删除。SHA256仅能发现传输损坏，**不能单独验证发行者身份**；正式面向公众自动分发前应确定**独立于 Android APK 私钥**的受控发布签名/可信公钥或等效供应链验证机制；没有机制就不假装已经安全签发。
- **不强制在线**：下载/检查更新在 Wi-Fi 或用户允许的网络条件下进行，出行中本地读取；GitHub/代理/NAS 不通时已安装知识包继续正常运行。GitHub 不是实时资料检索接口，也不是行车路况数据源。
- GitHub **Releases** 是长期发行档案；GitHub Actions 的临时 `artifacts` 用于测试报告/调试，**不作为永久成品保存**。发布二进制不进 Git 主历史，GitHub 正常仓库小文件、Release 发布大小限制遵循当时官方政策。未来需求超过 GitHub 限额时再迁对象存储/CDN，不在本版预建。
- **回滚/兼容性**：记录支持的 schema 和最低/最高兼容 App 版本；更改 Schema 要升级版本并提供转换，不直接重写已安装包；原始证据、生产工单、版本 tag、正式包 hash 应能逆向追溯。

## 8. 第一次实际运行的“最小黄金路径”

**先验证一个地区的小批次，别把全国爬虫、模型路由器、自动调度、数据库平台作为前置条件。**

- 用户在后续**明确授权**建设`KITT-PACKS`与制包流水线时，才创建仓库骨架、简单 Validator 和 Issue/PR 模板。
- 选**新都区内跨多领域的约5–10个对象**做一次人工可控试点；如果 #20 已产可用事实则以它作为样本，不重复抓取已核验资料；从中取约20–50条真实事实，来源质量不足宁可少。
- **第一次迭代可只用两个工具 + 人**：一个模型采集/提取，另一个模型独立打开来源核验兼做游客文风审稿，Codex/程序做格式与包构建，人抽查事实与试听。只有明确瓶颈后才拆更多 AI 角色。
- 首次发布实验要实际证明“另一台电脑/另一种AI 从 GitHub 的已接受源数据出发，在无需前一Agent聊天记录情况下**重建相同逻辑知识包**”，并输出可重现 SHA256；任何无法复现之处须说明时间戳、排序或依赖的原因。
- 试运行记录四个质量指标：**可复核事实比例、独立来源冲突/修订率、普通游客讲述合格率、单位有效事实的时间/模型调用成本**；此外量本地命中/实际断网讲述，不按生成总条数或 AI 调用数量论英雄。

## 9. 停止与接班

- 用户目前授权的是“**定义标准**”，并未授权部署`KITT-PACKS`、给 GitHub 授予新应用权限、批量抓取第三方资源、自动发布真实包或向手机安装。任何执行需后续任务卡和独立验收。
